# 4. Цель и концепция решения

4.1. Цели и обоснование необходимости развития

Цель - повысить понятность интерфейса системы с помощью запрета пользователям создавать заявки в одном ГК с одинаковым наименованием.

4.2. Описание проблем и решения

На текущий момент у пользователя существует возможность создания нескольких работ с одним и тем же наименованием в одном ГК , что может привести к недопонимаю среди участников процесса согласования расчетов стоимости и отчетной документации. Для решения проблемы предлагается запретить пользователям создавать заявки по одному ГК с одинаковым наименованием.

# 8. Функции системы

8.1. Создание алгоритма ФЛК для экранной формы создания заявки в части проверки номера заявки на дублирование

Необходимо реализовать алгоритм ФЛК для поля "Номер заявки" в экранной форме "Создание работы" (рис.1). Алгоритм должен не допускать заполнять поле "Номер заявки" значением, полностью совпадающим с любым из значений поля "Номер заявки" в ранее созданных работах в выбранном ГК.

При попытке заполнения поля подобным значением, должна появляться всплывающая ошибка с текстом "Заявка с таким номером уже существует в данном ГК".

Алгоритм так же должен запускаться при редактировании номера заявки в уже созданной заявке.

Необходимо создать ограничение на максимальную длину значения в поле "Номер заявки" в 3 символа.

8.2 Развитие функции сортировки в реестре работ в части изменения сортировки по умолчанию по времени создания работы

В реестре работ (рис.2) необходимо изменить правило сортировки по умолчанию. Сортировка должна производиться по времени создания работа, то есть чем позже время создания работы, тем выше строка в реестре (самые новые работы вверху, старые внизу).

8.3 Изменение логики создания работы: карточка созданной работы должна открываться сразу после сохранения новой работы

После успешного создания новой работы (при нажатии кнопки "Сохранить" в карточке создания работы (рис.2)), должна автоматически открываться карточка этой работы (рис. 3), а не реестр работ (рис. 2).
