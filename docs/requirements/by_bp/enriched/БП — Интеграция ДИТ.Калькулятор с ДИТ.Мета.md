### A.4 Цель и концепция решения

4.1.   Цели и обоснование необходимости развития

Цель – создать интеграцию между ДИТ.Калькулятор и ДИТ.Мета, чтобы Калькулятор мог запрашивать у Меты актуальную структуру для выбранной пользователем системы/БД и использовать эти данные для автоматического заполнения определённого набора полей ОИО.

Данные ДИТ.Мета будут использоваться не только для ОИО, но и в других разделах Дит.Калькулятора. Состав загружаемых атрибутов в будущем может расширяться.

4.2.   Описание проблем и решения

Сейчас, чтобы заполнить структурные поля ОИО (названия и назначение БД, перечень таблиц, перечень колонок с типами и признаком обязательности и т.п.), аналитик/подрядчик вручную сверяется со структурой БД и переносит данные в документ. Это приводит к: •    расхождениям между фактической структурой БД и тем, что написано в ОИО (человеческий фактор); •    временным затратам на ручной перенос; •    отсутствию единого источника правды – при изменении структуры БД никто не узнаёт, что ОИО устарел. Мета уже содержит эти данные (она регулярно сканирует промышленные БД и хранит их структуру с версионированием). Задача – не собирать эти данные заново, а взять их из Меты и поддерживать актуальность.

4.3. Границы решения В объём не входят: •    доработка ДИТ.Мета и ДИТ.Стат; •    изменение шаблона ОИО, в том числе удаление поля "Вид базы данных" – выполняют владельцы шаблона, Аналитик качества (ДИТ).

### A.9 Пользовательский сценарий и алгоритмы (п.7)

Сценарий 1. Ежедневная загрузка данных из ДИТ.Мета

Предусловие: наступило время ежедневной загрузки. Сценарий выполняется автоматически, без участия пользователя.

1. Система запрашивает у ДИТ.Мета актуальные опубликованные сведения о структуре БД систем (без объектов, помеченных в ДИТ.Мета как удалённые).
2. ДИТ.Мета передаёт сведения.
3. Система сохраняет полученные сведения с датой загрузки.
4. Система оставляет ранее загруженные сведения без изменений.

Исключения и ошибки:

1. Если ДИТ.Мета недоступна, система сохраняет последние загруженные сведения без изменений, фиксирует ошибку для администратора и повторяет загрузку при следующем запуске.
2. Е сли ДИТ.Мета недоступна, система разрешает пользователю заполнить необходмые поля вручную как раньше.

Сценарий 2. Создание документа ОИО и заполнение разделов 1–3

Предусловие: пользователь авторизован в системе, имеет доступ к объекту (подробнее: Матрица ролей и полномочий ) и находится основной вкладке "Работы".

1. Пользователь открывает необходимую Работу/Заявку из списка.
2. Система выводит экранную форму "Работа"/"Заявка".
3. Пользователь переходит на вкладку "План мероприятий" и открывает документ "Описание информационного обеспечения".
4. Система определяет систему по ID техпортала, вид проекта (СЗ или ГК) и применяет соответствующий шаблон ОИО.
5. Система при создании документа заполняет разделы 1–3 сведениями последней загрузки данных ДИТ.Мета по системе. На этом же шаге система подгружает и фиксирует в документе полный пул данных ДИТ.Мета по системе (в том числе перечень таблиц и колонок), который будет использоваться для заполнения раздела 4. На этом шаге данные для раздела 4 в интерфейсе не отображаются, они становятся видны и доступны пользователю только при открытии раздела 4 (сценарий 3).
6. Система сохраняет данные в карточке документа, фиксирует дату создания документа и дату загрузки данных (" Данные по состоянию на"), к которой привязаны сведения разделов 1– 4.

Исключения и ошибки:

4. Если по системе нет загруженных сведений из ДИТ.Мета, разделы 1–3 не заполняются, система выводит информационное сообщение: "Сведения из ДИТ.Мета по системе отсутствуют". Раздел 4 остаётся пустым. Пользователь заполняет данные вручную.

4. Если у системы нет актуальных БД, таблица состава БД остаётся пустой, количество БД – 0.

6. При повторном открытии документа данные не обновляются – используются сведения, зафиксированные при создании (или при последнем принудительном обновлении, подробнее в 2.1 и разделе 8.7).

7. Если систему ДИТ.Калькулятора не удалось сопоставить с системой в ДИТ.Мета (правило сопоставления – вопрос 5, Приложение), система действует как при отсутствии сведений (исключение 4): выводит сообщение "Сведения из ДИТ.Мета по системе отсутствуют", пользователь заполняет данные вручную.

Сценарий 2.1 Принудительное обновление данных в документе ОИО

Предусловие: пользователь авторизован в системе, имеет доступ к объекту (подробнее: Матрица ролей и полномочий ) и находится основной вкладке "Работы". Документ ОИО создан ранее (сценарий 2), с момента его появилась новая загрузка данных из ДИТ.Мета.

1. Пользователь открывает ранее созданный документ ОИО/карточки ОИО.
2. Система выводит сведения документа в том виде, в котором они были зафиксированы и дату "Данные по состоянию на".
3. Пользователь инициирует принудительное обновление данных (кнопка/действие "Обновить данные из ДИТ.Мета" – точное наименование определяется на этапе макетов).
4. Система проверяет наличие новой загрузки Меты по системе относительно загрузки, к которой привязан документ.
5. Если новая загрузка есть – система заменяет сведения разделов 1–4 данными последней загрузки, обновляет дату "Данные по состоянию на" и привязывает документ к новой загрузке.

Исключения и ошибки:

3. Если пользователь не обладает правом на обновление, действие недоступно.

4. Если во время обновления ДИТ.Мета недоступна – система выводит сообщение об ошибке, документ остаётся привязанным к прежней загрузке.

5. Если новой загрузки нет – система выводит сообщение "Новых данных из ДИТ.Мета по системе нет" и оставляет документ без изменений.

Сценарий 3. Выбор таблиц и заполнение раздела 4

Предусловие: документ ОИО создан (сценарий 2).

1. Пользователь открывает в документе ОИО раздел 4.
2. Система выводит перечень таблиц системы по сведениям, которыми заполнен документ.
3. Пользователь выбирает одну или несколько таблиц.
4. Система заполняет по каждой выбранной таблице её наименование и описание и формирует таблицу с составом колонок (п. 8.5).
5. Пользователь заполняет оставшиеся поля вручную.

Исключения и ошибки:

3. Если пользователь снимает выбор с таблицы, система удаляет её сведения из раздела 4.

3. Выбор таблиц для каждой БД обязателен, исключение – отсутствие таблиц в ДИТ.Мета в целом.

4. Если у таблицы или колонки нет описания в ДИТ.Мета, поле остаётся пустым.

5. При повторном открытии документа данные не обновляются – используются сведения, зафиксированные при создании.

Сценарий 4. Просмотр ранее созданного документа ОИО

Предусловие: документ ОИО создан ранее, осле его создания в ДИТ.Мета изменилась структура БД системы.

1. Пользователь открывает ранее созданный документ ОИО.
2. Система выводит сведения документа в том виде, в котором они были заполнены при создании.

Исключения и ошибки:

2. При повторном открытии документа данные не обновляются – используются сведения, зафиксированные при создании.

### A.10 Функции системы (п.8, дословно)

Функции доступны ролям Аналитик (ДИТ), Аналитик (Подрядчик) и Администратор. Аналитик (ДИТ), Аналитик (Подрядчик) – инициирование и просмотр, Администратор – все действия. Состав ролей и объём полномочий могут корректироваться, актуальные права приведены в Матрице ролей и полномочий (подробнее: Матрица ролей и полномочий ).

8.1. Ежедневная загрузка и хранение данных из ДИТ.Мета

Система должна обеспечивать (алгоритм – раздел 7, сценарий 1):

- ежедневную автоматическую загрузку данных из ДИТ.Мета о структурах БД систем (только опубликованных и только актуальных записей);
- сохранение каждой загрузки с датой загрузки; ранее загруженные сведения не изменяются и не удаляются (это обеспечивает историчность);
- сохранение последних загруженных сведений без изменений при недоступности ДИТ.Мета и повтор загрузки при следующем запуске.

Актуальной считается БД, которая в ДИТ.Мета не помечена как удалённая (признак deleted=false). Черновик изменённого описания в ДИТ.Мета видит только согласующий, поэтому при загрузке Калькулятор получает только согласованные описания. Предлагается загружать сведения только по системам, термин глоссария которых в ДИТ.Мета в статусе «Approved» (вопрос 8, Приложение). Загруженные из ДИТ.Мета сведения хранятся в Калькуляторе и будут использоваться не только для ОИО, но и в других разделах Калькулятора. Состав загружаемых атрибутов в будущем может расширяться, поэтому решение по загрузке и хранению должно позволять добавлять новые атрибуты ДИТ.Мета без переработки интеграции.

8.2. Заполнение состава и назначения БД

Система должна обеспечивать заполнение раздела 1 "Состав информационного обеспечения" документа ОИО (алгоритм – раздел 7, сценарий 2):

- перечень БД системы с полями "Наименование базы данных" и "Назначение базы данных";
- поле "Количество БД" – число актуальных БД системы; считаются БД всех сервисов системы: у одной системы может быть несколько сервисов (СУБД на разных вычислительных машинах).
- поле "Количество таблиц" – число таблиц во всех актуальных БД системы (правило подсчёта – вопрос 3, Приложение А) ;
- оставлять пустое значение, если в ДИТ.Мета у БД нет описания.

8.3. Определение типа СУБД

Система должна обеспечивать заполнение поля "Тип СУБД" в разделе 2.1 документа ОИО перечнем типов СУБД всех актуальных БД системы через запятую, каждый тип один раз, независимо от количества БД этого типа. Тип СУБД берётся из поля "serviceType" сервисов системы.  У одной системы может быть несколько сервисов – по одному на каждую СУБД на каждой вычислительной машине.

Пример:

| БД в системе | Значение поля "Тип СУБД" |
|---|---|
| 1 БД Oracle | Oracle |
| 3 БД Oracle | Oracle |

8.6. Фиксация данных в документе ОИО/карточке ОИО

Система должна обеспечивать (алгоритм – раздел 7, сценарии 2, 2.1 и 4):

- заполнение документа ОИО при его создании сведениями последней загрузки данных ДИТ.Мета;
- сохранение в карточке документа даты создания документа и даты загрузки данных  (например, поле "Данные по состоянию на");
- неизменность данных созданного документа при последующих загрузках из ДИТ.Мета и при повторном открытии документа до момента принудительного обновления (подробнее в разделе 8.7, сценарий 2.1). После принудительного обновления документ привязывается к новой загрузке, дальнейшее использование сведений документа идёт от неё;
- использование в разделе 4 (выбор таблиц) тех же сведений, которыми заполнен документ, а не более поздней загрузки.

Новый документ ОИО (например, по следующей Работе/Заявке) заполняется сведениями последней загрузки на дату его создания.

8.7. Принудительное обновление данных в документе ОИО

Система должна обеспечивать (алгоритм  – раздел 7, сценарий 2.1):

- возможность принудительно обновить данные ДИТ.Мета в уже созданном документе ОИО/карточке ОИО
- возможность пользователю запросить обновление, если документ создан ранее, с момента его создания появилась новая загрузка данных из ДИТ.Мета;
- при обновлении система заменяет сведения в документе ОИО/карточке ОИО в разделах 1– 4 (для 4 раздела необходим выбор пользователем конкретных таблиц) данными последней загрузки из ДИТ.Мета;
- дата в поле "Данные по состоянию на" в карточке документа обновляется на дату новой загрузки;
- документ привязывается к новой загрузке: дальнейшее заполнение и просмотр документа используют сведения этой загрузки;
- ранее зафиксированные в документе сведения перезаписываются (если потребуется история обновлений – вопрос в Приложении);
- обновление доступно ролям, имеющим доступ к объекту (подробнее: Матрица ролей и полномочий );
- если с момента последней привязки документа к загрузке новых загрузок данных из ДИТ.Мета по системе не было, система выводит информационное сообщение "Новых данных из ДИТ.Мета по системе нет" и оставляет документ без изменений.

### A.12 Внешние системы (п.10, дословно)

| Источник | Получатель | Какие данные | Когда |
|---|---|---|---|
| ДИТ.Мета | ДИТ.Калькулятор | Перечень систем и БД; структура БД систем: схемы, таблицы, колонки, их описания | Ежедневно, автоматически |

Калькулятор только получает данные и ничего не передаёт в ДИТ.Мета. К промышленным БД Калькулятор не подключается – это делает сама Мета. Состав данных, форматы и ролевая модель описаны в ФТ "Интеграция с ДИТ.Мета".

Версионность: каждый пакет метаданных сопровождается идентификатором пакета, датой и статусом (published/draft/archived). Калькулятор должен использовать только последний пакет со статусом published.

Технический способ получения данных определяют системный аналитик и архитектор.

Версионность простыми словами. ДИТ.Мета регулярно сканирует промышленные БД и хранит историю изменений их структуры: у каждого объекта есть номер версии (version) и дата изменения (updatedAt). Калькулятор при ежедневной загрузке берёт текущее состояние структуры и сохраняет его со своей датой загрузки. В требовании выше упомянуты пакеты со статусами «опубликован / черновик / архив»: в стандартной модели ДИТ.Мета таких пакетов нет (в маппинге атрибутов Меты – «частично покрыто»). Калькулятор берёт действующее состояние: объекты, не помеченные как удалённые. У каждого объекта есть номер версии (version) и дата изменения (updatedAt) – по ним видно, что изменилось с прошлой загрузки.

4.1.   Цели и обоснование необходимости развития

Цель – создать интеграцию между ДИТ.Калькулятор и ДИТ.Мета, чтобы Калькулятор мог запрашивать у Меты актуальную структуру для выбранной пользователем системы/БД и использовать эти данные для автоматического заполнения определённого набора полей ОИО.

Данные ДИТ.Мета будут использоваться не только для ОИО, но и в других разделах Дит.Калькулятора. Состав загружаемых атрибутов в будущем может расширяться.

4.2.   Описание проблем и решения

Сейчас, чтобы заполнить структурные поля ОИО (названия и назначение БД, перечень таблиц, перечень колонок с типами и признаком обязательности и т.п.), аналитик/подрядчик вручную сверяется со структурой БД и переносит данные в документ. Это приводит к: •    расхождениям между фактической структурой БД и тем, что написано в ОИО (человеческий фактор); •    временным затратам на ручной перенос; •    отсутствию единого источника правды – при изменении структуры БД никто не узнаёт, что ОИО устарел. Мета уже содержит эти данные (она регулярно сканирует промышленные БД и хранит их структуру с версионированием). Задача – не собирать эти данные заново, а взять их из Меты и поддерживать актуальность.

4.3. Границы решения В объём не входят: •    доработка ДИТ.Мета и ДИТ.Стат; •    изменение шаблона ОИО, в том числе удаление поля "Вид базы данных" – выполняют владельцы шаблона, Аналитик качества (ДИТ).

# 7. Пользовательский сценарий (путь)

Сценарий 1. Ежедневная загрузка данных из ДИТ.Мета

Предусловие: наступило время ежедневной загрузки. Сценарий выполняется автоматически, без участия пользователя.

1. Система запрашивает у ДИТ.Мета актуальные опубликованные сведения о структуре БД систем (без объектов, помеченных в ДИТ.Мета как удалённые).
2. ДИТ.Мета передаёт сведения.
3. Система сохраняет полученные сведения с датой загрузки.
4. Система оставляет ранее загруженные сведения без изменений.

Исключения и ошибки:

1. Если ДИТ.Мета недоступна, система сохраняет последние загруженные сведения без изменений, фиксирует ошибку для администратора и повторяет загрузку при следующем запуске.
2. Е сли ДИТ.Мета недоступна, система разрешает пользователю заполнить необходмые поля вручную как раньше.

Сценарий 2. Создание документа ОИО и заполнение разделов 1–3

Предусловие: пользователь авторизован в системе, имеет доступ к объекту (подробнее: Матрица ролей и полномочий ) и находится основной вкладке "Работы".

1. Пользователь открывает необходимую Работу/Заявку из списка.
2. Система выводит экранную форму "Работа"/"Заявка".
3. Пользователь переходит на вкладку "План мероприятий" и открывает документ "Описание информационного обеспечения".
4. Система определяет систему по ID техпортала, вид проекта (СЗ или ГК) и применяет соответствующий шаблон ОИО.
5. Система при создании документа заполняет разделы 1–3 сведениями последней загрузки данных ДИТ.Мета по системе. На этом же шаге система подгружает и фиксирует в документе полный пул данных ДИТ.Мета по системе (в том числе перечень таблиц и колонок), который будет использоваться для заполнения раздела 4. На этом шаге данные для раздела 4 в интерфейсе не отображаются, они становятся видны и доступны пользователю только при открытии раздела 4 (сценарий 3).
6. Система сохраняет данные в карточке документа, фиксирует дату создания документа и дату загрузки данных (" Данные по состоянию на"), к которой привязаны сведения разделов 1– 4.

Исключения и ошибки:

4. Если по системе нет загруженных сведений из ДИТ.Мета, разделы 1–3 не заполняются, система выводит информационное сообщение: "Сведения из ДИТ.Мета по системе отсутствуют". Раздел 4 остаётся пустым. Пользователь заполняет данные вручную.

4. Если у системы нет актуальных БД, таблица состава БД остаётся пустой, количество БД – 0.

6. При повторном открытии документа данные не обновляются – используются сведения, зафиксированные при создании (или при последнем принудительном обновлении, подробнее в 2.1 и разделе 8.7).

7. Если систему ДИТ.Калькулятора не удалось сопоставить с системой в ДИТ.Мета (правило сопоставления – вопрос 5, Приложение), система действует как при отсутствии сведений (исключение 4): выводит сообщение "Сведения из ДИТ.Мета по системе отсутствуют", пользователь заполняет данные вручную.

Сценарий 2.1 Принудительное обновление данных в документе ОИО

Предусловие: пользователь авторизован в системе, имеет доступ к объекту (подробнее: Матрица ролей и полномочий ) и находится основной вкладке "Работы". Документ ОИО создан ранее (сценарий 2), с момента его появилась новая загрузка данных из ДИТ.Мета.

1. Пользователь открывает ранее созданный документ ОИО/карточки ОИО.
2. Система выводит сведения документа в том виде, в котором они были зафиксированы и дату "Данные по состоянию на".
3. Пользователь инициирует принудительное обновление данных (кнопка/действие "Обновить данные из ДИТ.Мета" – точное наименование определяется на этапе макетов).
4. Система проверяет наличие новой загрузки Меты по системе относительно загрузки, к которой привязан документ.
5. Если новая загрузка есть – система заменяет сведения разделов 1–4 данными последней загрузки, обновляет дату "Данные по состоянию на" и привязывает документ к новой загрузке.

Исключения и ошибки:

3. Если пользователь не обладает правом на обновление, действие недоступно.

4. Если во время обновления ДИТ.Мета недоступна – система выводит сообщение об ошибке, документ остаётся привязанным к прежней загрузке.

5. Если новой загрузки нет – система выводит сообщение "Новых данных из ДИТ.Мета по системе нет" и оставляет документ без изменений.

Сценарий 3. Выбор таблиц и заполнение раздела 4

Предусловие: документ ОИО создан (сценарий 2).

1. Пользователь открывает в документе ОИО раздел 4.
2. Система выводит перечень таблиц системы по сведениям, которыми заполнен документ.
3. Пользователь выбирает одну или несколько таблиц.
4. Система заполняет по каждой выбранной таблице её наименование и описание и формирует таблицу с составом колонок (п. 8.5).
5. Пользователь заполняет оставшиеся поля вручную.

Исключения и ошибки:

3. Если пользователь снимает выбор с таблицы, система удаляет её сведения из раздела 4.

3. Выбор таблиц для каждой БД обязателен, исключение – отсутствие таблиц в ДИТ.Мета в целом.

4. Если у таблицы или колонки нет описания в ДИТ.Мета, поле остаётся пустым.

5. При повторном открытии документа данные не обновляются – используются сведения, зафиксированные при создании.

Сценарий 4. Просмотр ранее созданного документа ОИО

Предусловие: документ ОИО создан ранее, осле его создания в ДИТ.Мета изменилась структура БД системы.

1. Пользователь открывает ранее созданный документ ОИО.
2. Система выводит сведения документа в том виде, в котором они были заполнены при создании.

Исключения и ошибки:

2. При повторном открытии документа данные не обновляются – используются сведения, зафиксированные при создании.

## 7.1. [Пользовательские интерфейсы]

На данном этапе макеты не разрабатываются. БП запускает интеграцию с ДИТ.Мета, функционал работы пользователя с полученными данными будет уточняться по результатам запуска. Требования к интерфейсу оформляются отдельно, после согласования функционала.

При разработке макетов учесть: в карточке документа ОИО выводится поле "Данные по состоянию на" (дата загрузки данных ДИТ.Меты, которыми заполнен документ).

# 8. Функции системы

Функции доступны ролям Аналитик (ДИТ), Аналитик (Подрядчик) и Администратор. Аналитик (ДИТ), Аналитик (Подрядчик) – инициирование и просмотр, Администратор – все действия. Состав ролей и объём полномочий могут корректироваться, актуальные права приведены в Матрице ролей и полномочий (подробнее: Матрица ролей и полномочий ).

8.1. Ежедневная загрузка и хранение данных из ДИТ.Мета

Система должна обеспечивать (алгоритм – раздел 7, сценарий 1):

- ежедневную автоматическую загрузку данных из ДИТ.Мета о структурах БД систем (только опубликованных и только актуальных записей);
- сохранение каждой загрузки с датой загрузки; ранее загруженные сведения не изменяются и не удаляются (это обеспечивает историчность);
- сохранение последних загруженных сведений без изменений при недоступности ДИТ.Мета и повтор загрузки при следующем запуске.

Актуальной считается БД, которая в ДИТ.Мета не помечена как удалённая (признак deleted=false). Черновик изменённого описания в ДИТ.Мета видит только согласующий, поэтому при загрузке Калькулятор получает только согласованные описания. Предлагается загружать сведения только по системам, термин глоссария которых в ДИТ.Мета в статусе «Approved» (вопрос 8, Приложение). Загруженные из ДИТ.Мета сведения хранятся в Калькуляторе и будут использоваться не только для ОИО, но и в других разделах Калькулятора. Состав загружаемых атрибутов в будущем может расширяться, поэтому решение по загрузке и хранению должно позволять добавлять новые атрибуты ДИТ.Мета без переработки интеграции.

8.2. Заполнение состава и назначения БД

Система должна обеспечивать заполнение раздела 1 "Состав информационного обеспечения" документа ОИО (алгоритм – раздел 7, сценарий 2):

- перечень БД системы с полями "Наименование базы данных" и "Назначение базы данных";
- поле "Количество БД" – число актуальных БД системы; считаются БД всех сервисов системы: у одной системы может быть несколько сервисов (СУБД на разных вычислительных машинах).
- поле "Количество таблиц" – число таблиц во всех актуальных БД системы (правило подсчёта – вопрос 3, Приложение А) ;
- оставлять пустое значение, если в ДИТ.Мета у БД нет описания.

8.3. Определение типа СУБД

Система должна обеспечивать заполнение поля "Тип СУБД" в разделе 2.1 документа ОИО перечнем типов СУБД всех актуальных БД системы через запятую, каждый тип один раз, независимо от количества БД этого типа. Тип СУБД берётся из поля "serviceType" сервисов системы.  У одной системы может быть несколько сервисов – по одному на каждую СУБД на каждой вычислительной машине.

Пример:

| БД в системе | Значение поля "Тип СУБД" |
|---|---|
| 1 БД Oracle | Oracle |
| 3 БД Oracle | Oracle |
| 2 БД Oracle и 3 БД PostgreSQL | Oracle, PostgreSQL |

8.4. Заполнение внутренних справочников

раздела 3.1 "Перечень используемых категорий классификаторов и описание методов кодирования" документа ОИО

| № | Наименование справочника/классификатора | Тип | Назначение | Источник | Формат кодирования |
|---|---|---|---|---|---|
| 1 | Наименование справочника | Тип | Назначение | Источник | Формат кода |
| 2 | Наименование справочника | Тип | Назначение | Источник | Формат кода |

Система должна обеспечивать заполнение раздела 3.1 "Перечень используемых категорий классификаторов и описание методов кодирования" документа ОИО (алгоритм – раздел 7, сценарий 2):

- поле "Тип" = "Внутренний";
- поле "Наименование справочника/классификатора" –  наименование таблицы ( table_name) ;
- поле "Назначение" – описание таблицы ( table_description);

Признак "Справочник" будет заведён как дополнительное свойство таблицы или термин глоссария, теги не используются – их могут ставить только администраторы и архитекторы систем.

Пока признак в ДИТ.Мета не проставлен, пользователь отмечает справочники в разделе 3.1 вручную, выбирая таблицы системы; наименование и назначение подставляются из данных таблицы. После разметки в ДИТ.Мета строки с типом "Внутренний" заполняются автоматически.

Система должна обеспечивать заполнения раздела 4 "Организация внутримашинной информационной базы (описание физической и логической модели данных)" (алгоритм – раздел 7, сценарий 3):

- вывод перечня таблиц системы для выбора, в т.ч. нескольких таблиц сразу;
- заполнение по каждой выбранной таблице её наименования в виде "схема.таблица" (упоминается здесь: Методология проверки ОИО ) и описания. - формирование по каждой таблице перечня колонок в том порядке, в котором они идут в таблице: наименование, тип данных, обязательность, описание (у каждой колонки есть порядковый номер в таблице ordinalPosition);
- тип данных заполняется из data_type;
- удаление сведений таблицы из раздела 4, если пользователь снял с неё выбор.

8.6. Фиксация данных в документе ОИО/карточке ОИО

Система должна обеспечивать (алгоритм – раздел 7, сценарии 2, 2.1 и 4):

- заполнение документа ОИО при его создании сведениями последней загрузки данных ДИТ.Мета;
- сохранение в карточке документа даты создания документа и даты загрузки данных  (например, поле "Данные по состоянию на");
- неизменность данных созданного документа при последующих загрузках из ДИТ.Мета и при повторном открытии документа до момента принудительного обновления (подробнее в разделе 8.7, сценарий 2.1). После принудительного обновления документ привязывается к новой загрузке, дальнейшее использование сведений документа идёт от неё;
- использование в разделе 4 (выбор таблиц) тех же сведений, которыми заполнен документ, а не более поздней загрузки.

Новый документ ОИО (например, по следующей Работе/Заявке) заполняется сведениями последней загрузки на дату его создания.

8.7. Принудительное обновление данных в документе ОИО

Система должна обеспечивать (алгоритм  – раздел 7, сценарий 2.1):

- возможность принудительно обновить данные ДИТ.Мета в уже созданном документе ОИО/карточке ОИО
- возможность пользователю запросить обновление, если документ создан ранее, с момента его создания появилась новая загрузка данных из ДИТ.Мета;
- при обновлении система заменяет сведения в документе ОИО/карточке ОИО в разделах 1– 4 (для 4 раздела необходим выбор пользователем конкретных таблиц) данными последней загрузки из ДИТ.Мета;
- дата в поле "Данные по состоянию на" в карточке документа обновляется на дату новой загрузки;
- документ привязывается к новой загрузке: дальнейшее заполнение и просмотр документа используют сведения этой загрузки;
- ранее зафиксированные в документе сведения перезаписываются (если потребуется история обновлений – вопрос в Приложении);
- обновление доступно ролям, имеющим доступ к объекту (подробнее: Матрица ролей и полномочий );
- если с момента последней привязки документа к загрузке новых загрузок данных из ДИТ.Мета по системе не было, система выводит информационное сообщение "Новых данных из ДИТ.Мета по системе нет" и оставляет документ без изменений.

# 10. [ Взаимодействие с внешними ИС ]

| Источник | Получатель | Какие данные | Когда |
|---|---|---|---|
| ДИТ.Мета | ДИТ.Калькулятор | Перечень систем и БД; структура БД систем: схемы, таблицы, колонки, их описания | Ежедневно, автоматически |

Калькулятор только получает данные и ничего не передаёт в ДИТ.Мета. К промышленным БД Калькулятор не подключается – это делает сама Мета. Состав данных, форматы и ролевая модель описаны в ФТ "Интеграция с ДИТ.Мета".

Версионность: каждый пакет метаданных сопровождается идентификатором пакета, датой и статусом (published/draft/archived). Калькулятор должен использовать только последний пакет со статусом published.

Технический способ получения данных определяют системный аналитик и архитектор.

Версионность простыми словами. ДИТ.Мета регулярно сканирует промышленные БД и хранит историю изменений их структуры: у каждого объекта есть номер версии (version) и дата изменения (updatedAt). Калькулятор при ежедневной загрузке берёт текущее состояние структуры и сохраняет его со своей датой загрузки. В требовании выше упомянуты пакеты со статусами «опубликован / черновик / архив»: в стандартной модели ДИТ.Мета таких пакетов нет (в маппинге атрибутов Меты – «частично покрыто»). Нужно подтвердить у владельца ДИТ.Мета (вопрос 6, Приложение).

Сопоставление систем. Система в ДИТ.Мета – объект DatabaseService, её идентифицирует наименование. Код РИРС есть в Калькуляторе, но, по маппингу атрибутов Меты, в ДИТ.Мета не хранится. Надёжнее всего сопоставлять системы по коду РИРС, если его заведут в ДИТ.Мета (например, дополнительным свойством системы); сопоставление по наименованию ненадёжно (вопрос 5, Приложение).

Актуально: пакетов со статусами published / draft / archived для сервисов, БД, схем и таблиц в ДИТ.Мета нет – такие статусы есть только у глоссариев, KPI и подобных объектов (ответ владельца ДИТ.Мета). Калькулятор берёт действующее состояние: объекты, не помеченные как удалённые. У каждого объекта есть номер версии (version) и дата изменения (updatedAt) – по ним видно, что изменилось с прошлой загрузки.
