1. Сценарий работы с реестром "Закупки" (редактирование)

Предусловие: Пользователь авторизован в системе под ролью, которой доступно редактирование (уровень доступа указан в разделе 9 текущей постановки), и находится на главной странице ДИТ.Калькулятор

1. Пользователь переходит к "Расчет по Методике 3-Р/НСИ/Закупки" с реестром "Закупки" ( Если пользователю необходимо добавить запись, то переходим к шагу 2.1. Если пользователю необходимо редактировать запись, то переходим к шагу 3.1. Если пользователю необходимо удалить запись, то переходим к шагу 4.1);

2.1 Пользователь нажимает на кнопку "Добавить";

2.2 Пользователь заполняет поле Номер закупки на ЭФ "Введите номер закупки" ( Если пользователю необходимо продолжить, то переходим к шагу 2.3. Если пользователю необходимо вернуться к реестру, то переходим к шагу 2.4) ;

3.1 Пользователь кликает на строку с закупкой в реестре "Закупки" и нажимает кнопку "Редактировать";

3.2 Пользователь редактирует доступные поля на форме "Редактирование Закупки" (переходим к шагу 5);

4.1 Пользователь кликает на строку в реестре "Закупки" и нажимает на кнопку "Удалить" ( Если пользователь подтверждает удаление, то переходим к шагу 4.2, иначе к шагу 4.3);

4.2 Пользователь в модальном окне "Удаление" нажимает на кнопку "Да" (Система автоматически помечает данные как удаленные и не отображает на форме реестра) ( Конец сценария );

4.3 Пользователь в модальном окне "Удаление" нажимает на кнопку "Нет" (переходим к шагу 1);

5. Пользователь нажимает на кнопку "Сохранить" ( Конец сценария ).

## 7.2. Описание алгоритмов

#### 7.2.1 Алгоритм по обновлению данных в справочнике "Типы ГК"

Получение исходного значения Из атрибута "Тип контракта", переданного системой ДИТ.НСИ, выделяется часть, соответствующая полю "Тип ГК" (например, по правилу разделения: до определённого разделителя или по маске)

Проверка наличия в справочнике Система ДИТ.Калькулятор выполняет поиск полученного строкового значения в справочнике "Тип ГК":

- Сравнение производится без учёта регистра и лишних пробелов
- Если значение найдено - фиксируется его внутренний идентификатор (или само значение) для дальнейшей привязки к закупке

Добавление нового значения Если значение отсутствует в справочнике:

- Система автоматически создаёт новую запись в справочнике "Тип ГК"
- Новой записи присваивается уникальный идентификатор
- В поле "Наименование" записывается полученное значение

Привязка к закупке После подтверждения существования значения (найденного или вновь добавленного) система отображает в карточке закупки в ДИТ.Калькулятор значение из справочника "Тип ГК", соответствующее данной закупке

#### 7.2.2 Алгоритм по обновлению данных в справочнике "Подтипы ГК"

1. Получение исходного значения подтипа

Из атрибута "Тип контракта" выделяется часть, соответствующая полю "Подтип ГК" (по тому же правилу разделения, что и для типа)

2. Поиск значения подтипа в справочнике "Подтип ГК"

Система выполняет нормализованный поиск (без учёта регистра, лишних пробелов) по полю "Наименование"

- Если значение найдено – переходим к шагу 4
- Если не найдено – переходим к шагу 3

3. Добавление нового подтипа в справочник

Создаётся новая запись в справочнике "Подтип ГК" с уникальным идентификатором

В поле "Наименование" записывается полученное значение

Обязательно устанавливается внешняя связь: в поле "ID_Тип_ГК" новой записи проставляется идентификатор текущего Типа ГК (который был определён для этой закупки)

Тем самым фиксируется, что данный подтип принадлежит конкретному типу

4. Проверка допустимости подтипа для данного типа (валидация связи)

Даже если подтип найден в справочнике, необходимо убедиться, что он р азрешён для текущего Типа ГК:

1. Из записи найденного подтипа извлекается сохранённый

2. Сравнивается с идентификатором текущего Типа ГК

Если идентификаторы совпадают - подтип допустим, переходим к шагу 5

Если не совпадают (например, подтип ранее был создан для другого типа):

Варианты обработки (выбирается согласно бизнес-правилам системы):

- Отказ - закупка не принимается, логируется ошибка "Подтип не соответствует типу"
- Автоматическое пересоздание - система создаёт новую запись подтипа с таким же наименованием, но с привязкой к текущему типу (шаг 3). При этом старая запись остаётся для своего исходного типа
- Ручное вмешательство - закупка отправляется на верификацию оператору

#### 8.1.3 Доработка интеграции ДИТ.Калькулятор/ДИТ.НСИ/СПУ

1. Автоматическое обновление

Триггер: Ежедневно в 01:00

Исполнитель: Система ДИТ.Калькулятор

Сценарий:

1. В 01:00 каждого дня система Калькулятор инициирует процесс обновления реестра Закупки
2. Кальк отправляет запрос в НСИ на обновление данных
3. Валидация и ответ НСИ: НСИ проверяет наличие записей и отправляет отчет в Кальк
4. Обработка ответа (логика для Калька): Для каждой полученной Закупки из ответа НСИ: Проверить наличие Закупки в реестре Если закупка найдена в БД Калькулятора, то выполнить обновление всех полей в карточке Закупки данными из НСИ Если закупка не найден в БД Калькулятора, то выполнить создание новой записи в реестре Закупки
5. Логирование: По итогам цикла формируется запись в журнале синхронизации (количество обработанных, обновленных, добавленных записей)
6. Система помечает статус синхронизации как «Успешно»

Исключения:

1. Таймаут или ошибка НСИ: Если сервис НСИ не отвечает или отвечает ошибкой (5xx, 4xx), то процесс синхронизации останавливается, статус помечается как «Ошибка связи». Повторные попытки связи необходимо настроить по следующему принципу: 3 попытки с интервалом 10 минут, после чего необходима отправка уведомления администратору

2. Ручное обновление по номеру закупки

Триггер: Пользователь нажимает кнопку «Добавить» в интерфейсе реестра Закупки

Актор: Пользователи с ролями «Администратор НСИ», «Администратор»

Предусловие: Пользователь аутентифицирован и авторизован в системе ДИТ.Калькулятор

Сценарий:

1. Пользователь нажимает кнопку «Добавить» в реестре Закупки
2. Система отображает модальное окно со следующими элементами: Заголовок: «Введите номер закупки» Поле ввода: «Номер закупки» Кнопка «Применить» Кнопка «Отменить» Элемент закрытия модального окна
3. Пользователь вводит номер закупки
4. Система валидирует вводимые значения (возможно создание проверок для поля)
5. Пользователь нажимает на кнопку «Применить»
6. Кальк отправляет запрос с введенным пользователем номером закупки
7. Валидация ответа от НСИ: НСИ вернул запись об объекте: Кальк проводит поиск по номеру в реестре Закупки: Если запись с таким номером найдена, то система обновляет данные в карточке Закупки, закрывает модальное окно и отображает пользователю сообщение с текстом: «Данные по закупке <Номер закупки> успешно обновлены». Иначе система создает новую запись в реестре Закупки и отображает пользователю сообщение: «Закупка <Номер Закупки> создана» Логирование: Фиксируются действия пользователя

Исключения:

1. Если пользователь нажал «Применить», не введя номер закупки, то система подсвечивает поле ошибкой: «Необходимо ввести номер закупки»
2. Закупка не найден в НСИ: Если сервис НСИ отвечает ошибкой 404 или пустым телом ответа, то Кальк не создает и не обновляет записи в реестре и отображает пользователю сообщение об ошибке с текстом: «Ошибка обновления. Закупка с номером <Номер закупки> не найден. Проверьте корректность ввода или обратитесь к администратору сервиса» при этом модальное окно не закрывается и поле ввода активно
3. Таймаут или ошибка НСИ: Если сервис НСИ не отвечает или отвечает ошибкой (5xx), то Кальк отображает пользователю ошибку с текстом: «Временная ошибка. Повторите попытку позже»

При отработке интеграции создаются записи в реестре Закупки и Госконтракты. Далее система привязывает Закупки и Госконтракта по "Номеру ГК". После этого подтягивает из Закупки значение поля "Наименование системы" в Госконтракт для поля "Наименование системы"

## 7.2. Описание алгоритмов

#### 7.2.1 Алгоритм по обновлению данных в справочнике "Типы ГК"

Получение исходного значения Из атрибута "Тип контракта", переданного системой ДИТ.НСИ, выделяется часть, соответствующая полю "Тип ГК" (например, по правилу разделения: до определённого разделителя или по маске)

Проверка наличия в справочнике Система ДИТ.Калькулятор выполняет поиск полученного строкового значения в справочнике "Тип ГК":

- Сравнение производится без учёта регистра и лишних пробелов
- Если значение найдено - фиксируется его внутренний идентификатор (или само значение) для дальнейшей привязки к закупке

Добавление нового значения Если значение отсутствует в справочнике:

- Система автоматически создаёт новую запись в справочнике "Тип ГК"
- Новой записи присваивается уникальный идентификатор
- В поле "Наименование" записывается полученное значение

Привязка к закупке После подтверждения существования значения (найденного или вновь добавленного) система отображает в карточке закупки в ДИТ.Калькулятор значение из справочника "Тип ГК", соответствующее данной закупке

#### 7.2.2 Алгоритм по обновлению данных в справочнике "Подтипы ГК"

1. Получение исходного значения подтипа

Из атрибута "Тип контракта" выделяется часть, соответствующая полю "Подтип ГК" (по тому же правилу разделения, что и для типа)

2. Поиск значения подтипа в справочнике "Подтип ГК"

Система выполняет нормализованный поиск (без учёта регистра, лишних пробелов) по полю "Наименование"

- Если значение найдено – переходим к шагу 4
- Если не найдено – переходим к шагу 3

3. Добавление нового подтипа в справочник

Создаётся новая запись в справочнике "Подтип ГК" с уникальным идентификатором

В поле "Наименование" записывается полученное значение

Обязательно устанавливается внешняя связь: в поле "ID_Тип_ГК" новой записи проставляется идентификатор текущего Типа ГК (который был определён для этой закупки)

Тем самым фиксируется, что данный подтип принадлежит конкретному типу

4. Проверка допустимости подтипа для данного типа (валидация связи)

Даже если подтип найден в справочнике, необходимо убедиться, что он р азрешён для текущего Типа ГК:

1. Из записи найденного подтипа извлекается сохранённый

2. Сравнивается с идентификатором текущего Типа ГК

Если идентификаторы совпадают - подтип допустим, переходим к шагу 5

Если не совпадают (например, подтип ранее был создан для другого типа):

Варианты обработки (выбирается согласно бизнес-правилам системы):

- Отказ - закупка не принимается, логируется ошибка "Подтип не соответствует типу"
- Автоматическое пересоздание - система создаёт новую запись подтипа с таким же наименованием, но с привязкой к текущему типу (шаг 3). При этом старая запись остаётся для своего исходного типа
- Ручное вмешательство - закупка отправляется на верификацию оператору

#### 8.1.3 Доработка интеграции ДИТ.Калькулятор/ДИТ.НСИ/СПУ

1. Автоматическое обновление

Триггер: Ежедневно в 01:00

Исполнитель: Система ДИТ.Калькулятор

Сценарий:

1. В 01:00 каждого дня система Калькулятор инициирует процесс обновления реестра Закупки
2. Кальк отправляет запрос в НСИ на обновление данных
3. Валидация и ответ НСИ: НСИ проверяет наличие записей и отправляет отчет в Кальк
4. Обработка ответа (логика для Калька): Для каждой полученной Закупки из ответа НСИ: Проверить наличие Закупки в реестре Если закупка найдена в БД Калькулятора, то выполнить обновление всех полей в карточке Закупки данными из НСИ Если закупка не найден в БД Калькулятора, то выполнить создание новой записи в реестре Закупки
5. Логирование: По итогам цикла формируется запись в журнале синхронизации (количество обработанных, обновленных, добавленных записей)
6. Система помечает статус синхронизации как «Успешно»

Исключения:

1. Таймаут или ошибка НСИ: Если сервис НСИ не отвечает или отвечает ошибкой (5xx, 4xx), то процесс синхронизации останавливается, статус помечается как «Ошибка связи». Повторные попытки связи необходимо настроить по следующему принципу: 3 попытки с интервалом 10 минут, после чего необходима отправка уведомления администратору

2. Ручное обновление по номеру закупки

Триггер: Пользователь нажимает кнопку «Добавить» в интерфейсе реестра Закупки

Актор: Пользователи с ролями «Администратор НСИ», «Администратор»

Предусловие: Пользователь аутентифицирован и авторизован в системе ДИТ.Калькулятор

Сценарий:

1. Пользователь нажимает кнопку «Добавить» в реестре Закупки
2. Система отображает модальное окно со следующими элементами: Заголовок: «Введите номер закупки» Поле ввода: «Номер закупки» Кнопка «Применить» Кнопка «Отменить» Элемент закрытия модального окна
3. Пользователь вводит номер закупки
4. Система валидирует вводимые значения (возможно создание проверок для поля)
5. Пользователь нажимает на кнопку «Применить»
6. Кальк отправляет запрос с введенным пользователем номером закупки
7. Валидация ответа от НСИ: НСИ вернул запись об объекте: Кальк проводит поиск по номеру в реестре Закупки: Если запись с таким номером найдена, то система обновляет данные в карточке Закупки, закрывает модальное окно и отображает пользователю сообщение с текстом: «Данные по закупке <Номер закупки> успешно обновлены». Иначе система создает новую запись в реестре Закупки и отображает пользователю сообщение: «Закупка <Номер Закупки> создана» Логирование: Фиксируются действия пользователя

Исключения:

1. Если пользователь нажал «Применить», не введя номер закупки, то система подсвечивает поле ошибкой: «Необходимо ввести номер закупки»
2. Закупка не найден в НСИ: Если сервис НСИ отвечает ошибкой 404 или пустым телом ответа, то Кальк не создает и не обновляет записи в реестре и отображает пользователю сообщение об ошибке с текстом: «Ошибка обновления. Закупка с номером <Номер закупки> не найден. Проверьте корректность ввода или обратитесь к администратору сервиса» при этом модальное окно не закрывается и поле ввода активно
3. Таймаут или ошибка НСИ: Если сервис НСИ не отвечает или отвечает ошибкой (5xx), то Кальк отображает пользователю ошибку с текстом: «Временная ошибка. Повторите попытку позже»

При отработке интеграции создаются записи в реестре Закупки и Госконтракты. Далее система привязывает Закупки и Госконтракта по "Номеру ГК". После этого подтягивает из Закупки значение поля "Наименование системы" в Госконтракт для поля "Наименование системы"
