## Слой А. Структурированная карточка

### A.1 Термины и сокращения этой постановки

| Термин, сокращение | Определение |
|---|---|
| НСИ | Нормативно справочная информация |
| РСЗ | Расчет стоимости заявки |
| БП | Бизнес постановка |
| ФОИ | Функции обработки информации |

### A.2 Подсистемы

ДИТ.Интеллект, сервис Калькулятор:

Модуль "Расчет по методике 3-Р" Модуль "НСИ"

### A.3 Компоненты (объекты доработки)

Доработке подлежит:

Модальное окно "ФОИ Итерации"

Созданию подлежит:

Модуль "Реестр БП"

Модальное окно "Справочник БП по Системе"

### A.4 Цель и концепция решения

Цель: Предоставить возможность формировать  ФОИ по конкретным Бизнес-Постановкам вне Расчетов, а напрямую в новом реестре "Реестр БП". Обоснование необходимости: На данный момент вносить ФОИ и Прикреплять Бизнес-Постановки возможно только при создании Этапа и Расчета во вкладке "Работы", необходимо добавить Аналитику Подрядчика возможность прикреплять Бизнес-Постановки к Системе, а так же добавлять ФОИ по каждой прикрепленной постановке.

### A.5 Бизнес-цели и автоматизируемые процессы (из таблицы п.5)



Автоматизируемые процессы: Создание бизнес-постановки; Формирование ФОИ; Согласование бизнес-постановок; Интеграция с РСЗ; Управление записями реестра

### A.6 Пользовательские требования (User Stories)

- **УТ:** 1. Пользователь переходит в «НСИ -> Реестр БП». 2. Нажимает «Добавить» -> открывается «Редактор БП». 3. Выбирает «Госконтракт» из справочника. 4. Система: - Автозаполняет «Систему»; - Фильтрует «Подсистемы» по системе ГК; - Фильтрует «Функциональные требования» по ГК и отсутствию в согласованных БП. 5. Заполняет «Ссылка на Mos.Wiki», «Описание». 6. Нажимает «Сохранить».
- **УТ:** 1. В карточке БП нажимает «Добавить ФОИ». 2. Система: - Автозаполняет «Функциональное требование» из БП; - Фильтрует «Подсистемы» по выбранным в БП. 3. Заполняет «Уточняющая часть», «Краткое описание». 4. Перед сохранением система проверяет: - Уникальность «ФТ + Уточняющая часть» в рамках БП; - Отсутствие ФОИ в согласованных БП по ГК. 5. Нажимает «Сохранить».
- **УТ:** 1. Открывает БП в статусе «На согласовании». 2. Проверяет: - Корректность привязки к ГК; - Отсутствие дублирующих ФОИ в других согласованных БП. 3. Нажимает на индикатор статуса: - «Согласовано» -> сохраняет; - «На доработке» -> заполняет комментарий -> сохраняет. 4. Система: - Блокирует редактирование при согласовании; - Возвращает в «На доработке» при отклонении.
- **УТ:** 1. Открывает карточку РСЗ. 2. Во вкладке «ФОИ» нажимает «Выбрать из БП». 3. Система отображает список БП: - Статус «Согласовано»; - Привязка к системе текущего ГК. 4. Выбирает БП -> подтверждает. 5. Система копирует все ФОИ из БП в расчет.
- **УТ:** 1. В «Реестре БП» выбирает запись в статусе «В работе». 2. Для редактирования: - Нажимает «Редактировать»; - Изменяет ГК -> система сбрасывает подсистемы и ФТ; - Сохраняет изменения. 3. Для удаления: - Нажимает «Удалить»; - Система проверяет: -Отсутствие согласованных зависимостей; -Статус не «Согласовано». 4. Для БП в статусе «Согласовано» действия недоступны.

### A.9 Пользовательский сценарий и алгоритмы (п.7)

UC 1. Создание бизнес-постановки (БП) с привязкой к Госконтракту - Пользователь с ролью «Аналитик подрядчика»

1. Пользователь выбирает пункт меню «Расчет по методике 3-Р -> НСИ -> Реестр БП».
2. Нажимает кнопку «Добавить» -> открывается форма «Редактор БП».
3. Заполняет поля: - «Госконтракт» (выбор из справочника); - Система автоматически заполняется на основе ГК; - «Подсистемы» (выбор из списка, отфильтрованного по системе ГК); - «Функциональное требование» (выбор из списка, отфильтрованного по: -текущему ГК; -отсутствию в согласованных БП).
4. Нажимает «Добавить ФОИ».
5. В форме ФОИ: - «Функциональное требование» автозаполнено из БП; - «Подсистема» - выбор только из подсистем, указанных в БП; - Заполняет «Уточняющая часть», «Краткое описание».
6. Система проверяет: - Уникальность «ФТ + Уточняющая часть» в рамках БП; - Отсутствие ФОИ в согласованных БП по этому ГК.
7. Сохраняет ФОИ -> сохраняет БП.
8. Система создает запись в реестре со статусом «В работе». (Конец сценария)

UC 2. Управление БП (редактирование/удаление) - Пользователь с ролью «Аналитик подрядчика»

1. В «Реестре БП» выбирает БП в статусе «В работе» или «На доработке».
2. Для редактирования: - Нажимает «Редактировать» -> вносит изменения; - При смене ГК система сбрасывает подсистемы и ФТ, применяя новые фильтры.
3. Для удаления: - Нажимает «Удалить» -> подтверждает действие; - Система проверяет: -Отсутствие согласованных зависимостей; -Статус не «Согласовано».
4. Для БП в статусе «Согласовано»: - Действия «Редактировать»/«Удалить» недоступны. (Конец сценария)

UC 3. Перевод БП на согласование - Пользователь с ролью «Аналитик подрядчика»

1. Открывает карточку БП в статусе «В работе».
2. Проверяет, что все ФОИ имеют статус «Согласовано».
3. Нажимает на индикатор статуса -> выбирает «На согласовании».
4. Нажимает «Сохранить».
5. Система блокирует редактирование БП. (Конец сценария)

UC 4. Согласование/отклонение БП - Пользователь с ролью «Аналитик ДИТ»

1. Открывает БП в статусе «На согласовании».
2. Проверяет: - Корректность привязки к ГК; - Отсутствие дублирующих ФОИ в других согласованных БП.
3. Нажимает на индикатор статуса: - При согласовании: выбирает «Согласовано» -> сохраняет; - При отклонении: выбирает «На доработке», заполняет комментарий -> сохраняет.
4. Система: - При согласовании: делает БП доступной для РП в РСЗ; - При отклонении: возвращает БП в статус «На доработке» с комментарием аналитику подрядчика. (Конец сценария)

UC 5. Работа с ФОИ внутри БП - Пользователь с ролью «Аналитик подрядчика»

1. В карточке БП переходит во вкладку «ФОИ».
2. Для ФОИ в статусе «В работе»: - Нажимает «Редактировать» -> вносит изменения; - Переводит статус в «На согласовании» через индикатор.
3. Для согласования ФОИ: - Аналитик ДИТ проверяет данные и ставит статус «Согласовано» или «Отклонена».
4. Если ФОИ отклонена: - Статус возвращается в «На доработке» с комментарием. (Конец сценария)

Ключевые изменения:

- Удалены все упоминания РСЗ из сценариев аналитика подрядчика.
- Фокус на работе в Реестре БП : создание, управление статусами, согласование.
- Ролевая модель : - Аналитик подрядчика : работает с БП до согласования; - Аналитик ДИТ : согласует/отклоняет БП и ФОИ; - Руководитель проекта : получает доступ к согласованным БП только на этапе создания РСЗ (вне данного сценария).
- Валидация данных : - Фильтрация ФТ/подсистем по ГК; - Проверка дублей на уровне БП и согласованных записей.

### A.10 Функции системы (п.8, дословно)

8.1.1. Создание функции выбора значения из справочника для поля «Система» в модальном окне добавления БП

Назначение: Обеспечение корректной привязки БП к информационной системе через Госконтракт. Описание: - В форме «Редактор БП» (UC 1, шаг 3) поле «Система» автозаполняется после выбора «Госконтракта». - Выбор ГК ограничен справочником контрактов, где пользователь имеет роль «Аналитик подрядчика». - При изменении ГК система сбрасывает значения подсистем и ФТ.

8.1.2. Создание функции импорта информации (или файлов) пользователем для загрузки файла бизнес-постановки

Назначение: Прикрепление документации к БП в стандартизированном формате. Описание: - В форме «Редактор БП» реализована кнопка «Выбрать файл» для загрузки PDF/DOCX. - Система проверяет формат (.pdf, .doc, .docx).

8.1.3. Создание функции ввода информации пользователем через интерфейс системы для формы «Добавление новой ФОИ»

Назначение: Детализация ФОИ с наследованием данных из БП. Описание: - В форме ФОИ (UC 1, шаг 5) поля «Функциональное требование» и «Подсистема» автозаполняются или фильтруются на основе данных БП. - «Подсистема» отображает только значения, выбранные в карточке БП.

8.1.3. Развитие функции отображения информации пользователю в части изменения наименования полей, заголовков страниц и для автозаполнения полей «Система» и «Подсистема»

Назначение: Исключение неактуальных данных при редактировании БП. Описание: - При изменении ГК в карточке БП (UC 2, шаг 2) система сбрасывает подсистемы и ФТ, применяя новые фильтры. - Поля «Система» и «Подсистема» в ФОИ недоступны для редактирования.

8.2.1. Создание функции отображения информации пользователю в таком же виде, как она хранится во внутренних файлах ИС для реестра «Реестр БП»

Назначение: Наглядное представление данных в реестре. Описание: - После сохранения БП (UC 1, шаг 8) система отображает запись со столбцами: - Наименование БП; - Функциональное требование; - Сумма; - Госконтракт; - Статус. - Статусы визуализируются цветом: «В работе»-синий, «Согласовано»-зеленый.

8.2.2. Создание функции расчета значений показателей для поля «Сумма» в реестре БП

Назначение: Автоматизация расчета стоимости БП. Описание: - Сумма рассчитывается как сумма объемов работ по всем ФОИ с применением коэффициентов методики 3-Р. - Пересчет происходит при каждом сохранении БП (UC 1, шаг 8).

8.3.1. Создание функции отображения информации пользователю в таком же виде, как она хранится во внутренних файлах ИС для модального окна выбора БП

Назначение: Фильтрация согласованных БП по Госконтракту. Описание: - При создании РСЗ (вне зоны ответственности аналитика подрядчика) РП видит только БП в статусе «Согласовано», привязанные к системе текущего ГК.

8.3.2. Создание функции фильтрации для отображения БП по текущему Госконтракту и статусу

Назначение: Ограничение списка БП для РП. Описание: - Фильтрация учитывает привязку к ГК и статус.

8.3.3. Создание функции отображения информации с обработкой (изменением) исходных данных, хранимых в системе для автоматической загрузки ФОИ из БП

Назначение: Наследование данных из согласованных БП в РСЗ. Описание: - При выборе БП в РСЗ система копирует все её ФОИ с заполнением полей «Система», «Подсистема», «ФТ».

8.3.4. Создание функции проверки, которая не приводит к изменению данных при добавлении ФОИ в расчет

Назначение: Предотвращение дублирования ФОИ в РСЗ. Описание: - Система проверяет уникальность комбинации «ФТ + Уточняющая часть» в рамках одного РСЗ.

8.4.1. Создание функции ввода информации пользователем через интерфейс системы для управления записями реестра

Назначение: Управление БП (редактирование/удаление) аналитиком подрядчика. Описание: - В реестре БП кнопки «Редактировать» и «Удалить» активны только для записей в статусах «В работе» и «На доработке» (UC 2). - При удалении система проверяет отсутствие привязки к согласованным РСЗ.

8.4.2. Создание функции проверки (контроля), которые не приводят к изменению данных при удалении БП

Назначение: Блокировка удаления согласованных БП. Описание: - При попытке удалить БП в статусе «Согласовано» система выводит ошибку «Удаление запрещено для согласованных записей».

8.4.3. Создание функции проверки (контроля), которые не приводят к изменению данных при добавлении ФОИ в БП

Назначение: Проверка дублей ФОИ внутри БП и в согласованных записях. Описание: - Система проверяет: - Уникальность «ФТ + Уточняющая часть» в рамках одной БП (UC 3, шаг 6); - Отсутствие ФОИ в согласованных БП по текущему ГК.

# 7. Пользовательский сценарий (путь)

UC 1. Создание бизнес-постановки (БП) с привязкой к Госконтракту - Пользователь с ролью «Аналитик подрядчика»

1. Пользователь выбирает пункт меню «Расчет по методике 3-Р -> НСИ -> Реестр БП».
2. Нажимает кнопку «Добавить» -> открывается форма «Редактор БП».
3. Заполняет поля: - «Госконтракт» (выбор из справочника); - Система автоматически заполняется на основе ГК; - «Подсистемы» (выбор из списка, отфильтрованного по системе ГК); - «Функциональное требование» (выбор из списка, отфильтрованного по: -текущему ГК; -отсутствию в согласованных БП).
4. Нажимает «Добавить ФОИ».
5. В форме ФОИ: - «Функциональное требование» автозаполнено из БП; - «Подсистема» - выбор только из подсистем, указанных в БП; - Заполняет «Уточняющая часть», «Краткое описание».
6. Система проверяет: - Уникальность «ФТ + Уточняющая часть» в рамках БП; - Отсутствие ФОИ в согласованных БП по этому ГК.
7. Сохраняет ФОИ -> сохраняет БП.
8. Система создает запись в реестре со статусом «В работе». (Конец сценария)

UC 2. Управление БП (редактирование/удаление) - Пользователь с ролью «Аналитик подрядчика»

1. В «Реестре БП» выбирает БП в статусе «В работе» или «На доработке».
2. Для редактирования: - Нажимает «Редактировать» -> вносит изменения; - При смене ГК система сбрасывает подсистемы и ФТ, применяя новые фильтры.
3. Для удаления: - Нажимает «Удалить» -> подтверждает действие; - Система проверяет: -Отсутствие согласованных зависимостей; -Статус не «Согласовано».
4. Для БП в статусе «Согласовано»: - Действия «Редактировать»/«Удалить» недоступны. (Конец сценария)

UC 3. Перевод БП на согласование - Пользователь с ролью «Аналитик подрядчика»

1. Открывает карточку БП в статусе «В работе».
2. Проверяет, что все ФОИ имеют статус «Согласовано».
3. Нажимает на индикатор статуса -> выбирает «На согласовании».
4. Нажимает «Сохранить».
5. Система блокирует редактирование БП. (Конец сценария)

UC 4. Согласование/отклонение БП - Пользователь с ролью «Аналитик ДИТ»

1. Открывает БП в статусе «На согласовании».
2. Проверяет: - Корректность привязки к ГК; - Отсутствие дублирующих ФОИ в других согласованных БП.
3. Нажимает на индикатор статуса: - При согласовании: выбирает «Согласовано» -> сохраняет; - При отклонении: выбирает «На доработке», заполняет комментарий -> сохраняет.
4. Система: - При согласовании: делает БП доступной для РП в РСЗ; - При отклонении: возвращает БП в статус «На доработке» с комментарием аналитику подрядчика. (Конец сценария)

UC 5. Работа с ФОИ внутри БП - Пользователь с ролью «Аналитик подрядчика»

1. В карточке БП переходит во вкладку «ФОИ».
2. Для ФОИ в статусе «В работе»: - Нажимает «Редактировать» -> вносит изменения; - Переводит статус в «На согласовании» через индикатор.
3. Для согласования ФОИ: - Аналитик ДИТ проверяет данные и ставит статус «Согласовано» или «Отклонена».
4. Если ФОИ отклонена: - Статус возвращается в «На доработке» с комментарием. (Конец сценария)

Ключевые изменения:

- Удалены все упоминания РСЗ из сценариев аналитика подрядчика.
- Фокус на работе в Реестре БП : создание, управление статусами, согласование.
- Ролевая модель : - Аналитик подрядчика : работает с БП до согласования; - Аналитик ДИТ : согласует/отклоняет БП и ФОИ; - Руководитель проекта : получает доступ к согласованным БП только на этапе создания РСЗ (вне данного сценария).
- Валидация данных : - Фильтрация ФТ/подсистем по ГК; - Проверка дублей на уровне БП и согласованных записей.

# 8. Функции системы

8.1.1. Создание функции выбора значения из справочника для поля «Система» в модальном окне добавления БП

Назначение: Обеспечение корректной привязки БП к информационной системе через Госконтракт. Описание: - В форме «Редактор БП» (UC 1, шаг 3) поле «Система» автозаполняется после выбора «Госконтракта». - Выбор ГК ограничен справочником контрактов, где пользователь имеет роль «Аналитик подрядчика». - При изменении ГК система сбрасывает значения подсистем и ФТ.

8.1.2. Создание функции импорта информации (или файлов) пользователем для загрузки файла бизнес-постановки

Назначение: Прикрепление документации к БП в стандартизированном формате. Описание: - В форме «Редактор БП» реализована кнопка «Выбрать файл» для загрузки PDF/DOCX. - Система проверяет формат (.pdf, .doc, .docx).

8.1.3. Создание функции ввода информации пользователем через интерфейс системы для формы «Добавление новой ФОИ»

Назначение: Детализация ФОИ с наследованием данных из БП. Описание: - В форме ФОИ (UC 1, шаг 5) поля «Функциональное требование» и «Подсистема» автозаполняются или фильтруются на основе данных БП. - «Подсистема» отображает только значения, выбранные в карточке БП.

8.1.3. Развитие функции отображения информации пользователю в части изменения наименования полей, заголовков страниц и для автозаполнения полей «Система» и «Подсистема»

Назначение: Исключение неактуальных данных при редактировании БП. Описание: - При изменении ГК в карточке БП (UC 2, шаг 2) система сбрасывает подсистемы и ФТ, применяя новые фильтры. - Поля «Система» и «Подсистема» в ФОИ недоступны для редактирования.

8.2.1. Создание функции отображения информации пользователю в таком же виде, как она хранится во внутренних файлах ИС для реестра «Реестр БП»

Назначение: Наглядное представление данных в реестре. Описание: - После сохранения БП (UC 1, шаг 8) система отображает запись со столбцами: - Наименование БП; - Функциональное требование; - Сумма; - Госконтракт; - Статус. - Статусы визуализируются цветом: «В работе»-синий, «Согласовано»-зеленый.

8.2.2. Создание функции расчета значений показателей для поля «Сумма» в реестре БП

Назначение: Автоматизация расчета стоимости БП. Описание: - Сумма рассчитывается как сумма объемов работ по всем ФОИ с применением коэффициентов методики 3-Р. - Пересчет происходит при каждом сохранении БП (UC 1, шаг 8).

8.3.1. Создание функции отображения информации пользователю в таком же виде, как она хранится во внутренних файлах ИС для модального окна выбора БП

Назначение: Фильтрация согласованных БП по Госконтракту. Описание: - При создании РСЗ (вне зоны ответственности аналитика подрядчика) РП видит только БП в статусе «Согласовано», привязанные к системе текущего ГК.

8.3.2. Создание функции фильтрации для отображения БП по текущему Госконтракту и статусу

Назначение: Ограничение списка БП для РП. Описание: - Фильтрация учитывает привязку к ГК и статус.

8.3.3. Создание функции отображения информации с обработкой (изменением) исходных данных, хранимых в системе для автоматической загрузки ФОИ из БП

Назначение: Наследование данных из согласованных БП в РСЗ. Описание: - При выборе БП в РСЗ система копирует все её ФОИ с заполнением полей «Система», «Подсистема», «ФТ».

8.3.4. Создание функции проверки, которая не приводит к изменению данных при добавлении ФОИ в расчет

Назначение: Предотвращение дублирования ФОИ в РСЗ. Описание: - Система проверяет уникальность комбинации «ФТ + Уточняющая часть» в рамках одного РСЗ.

8.4.1. Создание функции ввода информации пользователем через интерфейс системы для управления записями реестра

Назначение: Управление БП (редактирование/удаление) аналитиком подрядчика. Описание: - В реестре БП кнопки «Редактировать» и «Удалить» активны только для записей в статусах «В работе» и «На доработке» (UC 2). - При удалении система проверяет отсутствие привязки к согласованным РСЗ.

8.4.2. Создание функции проверки (контроля), которые не приводят к изменению данных при удалении БП

Назначение: Блокировка удаления согласованных БП. Описание: - При попытке удалить БП в статусе «Согласовано» система выводит ошибку «Удаление запрещено для согласованных записей».

8.4.3. Создание функции проверки (контроля), которые не приводят к изменению данных при добавлении ФОИ в БП

Назначение: Проверка дублей ФОИ внутри БП и в согласованных записях. Описание: - Система проверяет: - Уникальность «ФТ + Уточняющая часть» в рамках одной БП (UC 3, шаг 6); - Отсутствие ФОИ в согласованных БП по текущему ГК.
