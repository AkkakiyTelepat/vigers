4.1. Цели и обоснование необходимости развития

Для удобства и скорости работы необходимо реализовать три ключевых возможности: просмотр расширенной информации по ГК (чтобы анализировать контракт без внешних источников), заполнение данных о подрядчике, заказчике и ФЗ на одной вкладке (для централизации ввода и снижения ошибок), а также работу с коэффициентами МТ без лишних переходов в карточке подсистемы (ускоряет процесс и снижает нагрузку на пользователя). Если сведения по ГК отсутствуют, пользователь должен иметь возможность заполнить поля вручную . Сущность "Закупки" должна быть связана с с сущностью "Государственный контракт" через Номер ГК

8.2 Развитие ЭФ "Редактор ГК" в части различного отображения для разных типов работ по ГК

На экранной форме "Редактор ГК" во вкладке "Доп. сведения по ГК" необходимо добавить подвкладку с типом работ "Создание/развитие" (рис. 4), в дальнейшем будут добавляться новые подвкладки, например для работ по эксплуатации, ИБ и тд. По умолчанию ГК создаются только с подвкладкой "Создание/развитие", после добавления новых Типов работ в ДИТ.Кальклятор будет актуализирован список подвкладок.

Необходимо модернизировать ЭФ "Редактор ГК" в части различных вариантов её отображения в зависимости от того предусмотрены ли работы по рефакторингу для данного ГК, реализация вариантов отображения должна быть реализована через активацию нового чек-бокса " Контракт предусматривает наличие работ по рефакторингу " (рис.4):

1) В случае если чек-бокс активен - функциональный блок "Рефакторинг" отображается на ЭФ (рис. 4)

2) В случае если чек-бокс не активен - функциональный блок "Рефакторинг" скрыт с ЭФ (рис. 5)

8.3 Создание алгоритмов ФЛК для полей вкладки "Доп. сведения" в редакторе ГК

Необходимо создать алгоритмы ФЛК для полей блоков "Создание/Развитие" и "Рефакторинг" на ЭФ "Редактор ГК" во вкладке "Доп. сведения по ГК" в подвкладке "Создание/Развитие".

Суть работы алгоритма:

1) ФЛК при отсутствии работ по рефакторингу в ГК (чек-бокс не активен):

Поля:

- Стоимость 1 чел-мес работ по созданию / развитию Системы, руб
- Итого количество функц. точек на создание / развитие Системы
- Общие расчетные трудозатраты на создание / развитие Системы

Значения перечисленных полей не должны быть равны 0 или пустыми.

- коэффициент пересчета:

Значение должно быть больше 0 и не превышать 1.

2) ФЛК при наличии работ по рефакторингу в ГК (чек-бокс активен):

Поля:

- Стоимость 1 чел-мес работ по созданию / развитию Системы, руб
- Итого количество функц. точек на создание / развитие Системы
- Общие расчетные трудозатраты на создание / развитие Системы
- Стоимость 1 чел-мес работ по рефакторингу функций Системы, руб
- Итого количество функц. точек на рефакторинг функций Системы
- Общие расчетные трудозатраты на рефакторинг функций Системы

Значения перечисленных полей не должны быть равны 0 или пустыми.

- коэффициент пересчета:

Значение должно быть больше 0 и не превышать 1.

Результат работы алгоритма:

В случае если значение хотя бы одно из перечисленных выше полей не соответствует описанным требованиям:

- Перевод ГК в статус "На согласовании РП" блокируется
- Пользователю высвечивается всплывающая системная ошибка при попытке перевести статус из "Черновик" в "Согласование РП" (статусная модель описана в постановке БП - Создание статусной модели для Закупки, ГК, Этапа ГК и Работа/Заявка )

8.4 Развитие ЭФ "Редактор ГК" в части объединения вкладок  "Информация о подрядчике", "Информация о ФЗ", "Информация о заказчике", добавления новых атрибутов контракта

Необходимо объединить вкладки  "Информация о подрядчике", "Информация о ФЗ", "Информация о заказчике" в одну вкладку "Подписанты" (рис. 6). Логика заполнения данных в новой вкладке при этом должна остаться без изменений, кроме вкладки "Информация о ФЗ".

Логика заполнения "Информации о ФЗ":

1. Пользователь переходит на ЭФ "Редактор ГК" вкладка "Подписанты" раздел "Функциональный заказчик" и нажимает кнопку "Добавить"

1.1 Система отображает пользователю форму "Добавление ФЗ"

2. Пользователь выбирает организацию в поле "Наименование организации функционального заказчика" и нажимает на кнопку "Добавить"

2.1 Система отображает пользователю форму "Добавить подписанта от функционального заказчика"

3. Пользователь выбирает в реестре запись и нажимает на кнопку "Выбрать"

3.1 Система закрывает форму "Добавить подписанта от функционального заказчика" и отображает форму "Добавление ФЗ" с новой записью в реестре "Подписанты от функционального заказчика"

- коэффициент пересчета:

8.6 Развитие ЭФ "Карточка подсистемы" из реестра подсистем в части переработки отображения коэффициентов

ЭФ "Карточка подсистемы" (путь: Расчет по методике 3-р => НСИ => Реестр подсистем =>Карточка подсистемы) должна быть переработана:

1. Карточка должна по умолчанию отображаться в полноэкранном режиме (рис. 10).
2. Поля "Уровень языка разработки" и "Коэффициент преобразования ФТ в РР" должны быть объединены в функциональный блок "Коэффициенты для старой версии Методики 3-Р" (рис. 10). Функциональный блок должно быть возможно свернуть/развернуть нажав на соответствующий символ рядом с наименованием блока (рис.10).
3. Функциональный блок "Коэффициенты для расчета по Методике 3-Р" должен быть переделан в части отображения заведенных коэффициентов для каждого существующего ГК (значения и наименования для всех существующих ГК должны автоматически подтягиваться) (рис. 10). Редактирование полей функционального блока должно осуществляться внутри карточки коэффициентов, которая открывается при нажатии на строку соответствующего ГК (логика работы не меняется).  Логика работы кнопок "Обновить", "Добавить", "Добавить на основе", "Редактировать" так же не меняется.
