# 06. Нефункциональные требования (NFR)

Документы репозитория содержат преимущественно функциональные постановки; NFR извлечены из разделов «Требования к интерфейсу» (7), «Описание алгоритмов» (5), «Информационная безопасность и разграничение доступа» (10 — заполнен частично), а также явных упоминаний в тексте. Всё, что не указано в источниках, помечено как «не задано».

## 6.1. Интерфейс и UX
- Стандартный блок пагинации во всех реестрах: количество всех записей и записей на странице, навигация по страницам при >1 страницы (`БП - Создание реестра _Закупки_`, `БП - Календарный план ГК/СЗ` и др.).
- Единое выравнивание содержимого столбцов реестров по типу данных (`БП - Выравнивание реестров`).
- Адаптивность: полный доступ к данным таблиц без блокировки нижней панелью; устранение горизонтальной прокрутки модальных окон (`БП - _Сделать интерфейс… адаптивным…`).
- Цветовая индикация статусов и состояний: подсветка строк по статусу ФОИ (зелёный/жёлтый/красный), индикатор кнопки проверки коэффициентов (серый→зелёный), цветовые карточки сценариев обучения, красная/зелёная подсветка просрочек (`БП - Конструктор РСЗ`, `БП - Проверка заполненности НСИ…`, `БП - База Знаний Калькулятора`, `БП - Календарный план ГК/СЗ`).
- Модальные окна уведомлений: текст доступен для выделения и копирования, скролл при переполнении, по возможности динамический размер (`БП - Проверка заполненности НСИ…`).
- Подсказки (тултипы): к обязательным полям (файл БП), к индикаторам (методика расчёта), при наведении на значок статуса проверок ФОИ (`БП - Выравнивание реестров`, `Бизнес постановка на добавление подсказок в индикаторы`, `БП - Статус ФОИ с фиксированной стоимостью`).
- Состояние пустого реестра: сообщение «Данные для отображения отсутствуют. Для создания новой записи, воспользуйтесь действием "Добавить"» (`БП — Объединение реестров…`).
- Макеты экранной формы прилагаются к каждой БП (раздел «Приложения», рисунки); соответствие макету контролируется критериями приемки.

## 6.2. Интеграционные / технические требования
- Периодичность обменов: СПУ/Техпортал — ежедневно 23:00 + очередь каждые 5 минут; ДИТ.Мета — ежедневно; Telegram — интервал не определён однозначно (см. C-4).
- Отказоустойчивость: ретраи 3× с интервалом 10 минут и уведомлением администратора (ДИТ.НСИ); обработка недоступности API СПУР с режимом «частично успешной операции» и автоповтором; контроль рассинхронизации службой сопровождения (E1 СПУР).
- Идемпотентность и трассировка: защита от повторной обработки одного сообщения и дублирующего создания экземпляров; correlationId в каждом вызове между Калькулятором и СПУР; аудит действий.
- Внутренняя реализация (упомянуто в источниках): серверный метод `ServerMethodGetPOZReportDataService` генерирует json-объект для подстановки в шаблоны ПОЗ; очередь на скачивание файлов; Telegram-бот @dit_int_bot для обращений в ДИТ.Вопрос.
- Форматы файлов: импорт ФОИ — Excel; выгрузки замечаний/реестра замен — Excel; шаблоны ОД — .docx с тегами подстановки ({sum}, {issue_personMonths} и др.); предпросмотр документов — PDF/изображения/текст; вложения Базы знаний — JPEG/PNG/GIF/SVG, PDF, DOCX.

## 6.3. Информационная безопасность и разграничение доступа
- Раздел 10 «Информационная безопасность и разграничение доступа» присутствует в структуре БП, но в большинстве документов **не заполнен** (шаблонные пункты: 10.1 требования к обеспечению защиты информации, 10.2 требования к защите от НСД, 10.3 требования к антивирусной защите — без содержания).
- Фактические требования безопасности сведены к ролевой модели (см. файл 02) и отдельным правилам: проверка прав на публикацию (Telegram), права на обновление данных (ДИТ.Мета), права на перевод статусов (статусные модели), видимость статей/папок по ролям (База знаний), скрытие столбца «Стоимость» для всех кроме Администратора, блокирование редактирования в согласованных статусах.
- Конкретные меры (шифрование, аутентификация, журналы аудита вне СПУР-интеграции, ПДн) — **не заданы ни в одном документе**.

## 6.4. Производительность и объёмы
- Прямых числовых требований (время отклика, TPS, объёмы данных) в документах нет. Косвенные указания: массовые операции (перепривязка всех согласованных ФОИ при создании итерации; пакетный импорт Систем из НСИ с журналом), динамический размер модального окна при множестве подсистем, пагинация больших реестров, «по возможности» формулировки. → см. OI-6 (отсутствие измеримых NFR).

## 6.5. Требования к данным и справочникам
- Обязательность и форматы зафиксированы точечно: «Номер ГК» ≤ 20 символов; «Номер заявки» ≤ 3 символов; порядковый регистрационный номер системы — 3 цифры 001–999; признак машинных носителей — символ «М»; описание ФОИ ≥ 300 символов; коэффициент пересчета 0 < k ≤ 1; МТ1–МТ8 ровно 8 ненулевых значений; доли загрузки сотрудников ∈ {0,25; 0,5; 1}; округление чел.-мес. до 2 знаков.
- Уникальность: пара «наименование+ссылка» в Закупках; отсутствие дублей наименований работ в рамках ГК; дубли US допускаются только с обоснованием.
- Единообразие представления отсутствия данных: «undefined» в печатных формах (BR-DATA-01/02).
- Хранение истории: история статусов ФОИ фиксированной стоимости; старые экземпляры документов СПУР не удаляются; прослеживаемость замен ФОИ (исходное значение сохраняется).

## 6.6. Эксплуатация и поддержка
- Канал поддержки: обращения в СТП (откат согласованных расчётов, частные случаи НДС, удаление/правка данных); редирект «Обратиться в ДИТ.Вопрос» → Telegram-бот; эскалация чат-бота раздела «Помощь» оператору.
-ведомость дефектов, зафиксированных как задачи: DITINT-2153 (НДС), DITINT-2272 (дубли US), DITINT-2261 (печатная форма без замен), DITINT-3417 (несоответствия шаблонов ПМИ).

## 6.7. Регламенты использования (из источников)
- Дашборд бюджетов: регулярность использования — ежедневно; типичная сессия — просмотр показателей; целевые роли — РП, руководители направлений/продуктов.
- Онбординг: презентация при первом входе (кроме Администратора).
- Синхронизации запускаются автоматически; ручные запуски — привилегия Администратора.
