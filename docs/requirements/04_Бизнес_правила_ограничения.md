# 04. Бизнес-правила, ограничения и исключения (Business Rules & Constraints)

## 4.1. Статусные модели: Закупка, ГК, Этап ГК, Работа/Заявка (`БП - Создание статусной модели для Закупки, ГК, Этапа ГК и Работа_Заявка`)

### 4.1.1. Закупка
| Статус | Как присваивается | Куда можно перевести | Кто переводит |
|---|---|---|---|
| В работе | Автоматически при условии «Номер ГК» = NULL И «Закупка от …» (условие усечено в источнике) | Авто: Завершено, Отменено; вручную: Корзина | Система / Администратор |
| Завершено | Автоматически при «Номер ГК» ≠ NULL ИЛИ вручную | Авто: Архив; вручную: Корзина | Система / Администратор |
| Архив | Автоматически после изменения в связанном Госконтракте статуса… | — | Система / Администратор |
| Корзина | Вручную из «Завершено» и «В работе» | Вручную: В работе, Завершено | Администратор |

Примечание: в сводном описании той же БП упоминается также переход «Отменено» — отдельная строка таблицы статусов в источнике отсутствует (см. 07, Ambiguity A-2).

### 4.1.2. Государственный контракт
| Статус | Как присваивается | Куда переводится | Кто |
|---|---|---|---|
| Черновик | Автоматически: система сравнивает полученные данные… | Вручную: Корзина, Согласование РП | Система; Администратор, Руководитель проекта (ДИТ) |
| Согласование РП | Вручную из «Черновик» после проверки заполнения обязательных полей | Вручную: Корзина, Согласование РП, Черновик | Администратор |
| В работе | Вручную при условии ИЛИ после проверки заполнения сведений | Вручную: Корзина, Исполнено | Руководитель проекта (ДИТ), Администратор |
| Исполнено | Автоматически: все Этапы, связанные с ГК, в статусе… | Авто: Архив | Система; Администратор |
| Архив | Автоматически через **10 календарных дней** после проставления статуса «Исполнено» | — | Система; Администратор |
| Корзина | Вручную из «Черновик», «Согласование РП», иных статусов | Вручную: Черновик, Согласование РП, В работе, Исполнено | Администратор |

### 4.1.3. Этап ГК
| Статус | Присвоение | Переходы | Кто |
|---|---|---|---|
| Черновик | Автоматически при создании | Авто: В работе; вручную: Корзина | Система; Администратор |
| В работе | Автоматически при переводе ГК в «В работе» | Авто: Оплачено; вручную: Корзина | Система; Администратор |
| Оплачен(о) | Автоматически, если Stage Points/Name = «Оплата по…» (данные СПУ) | — ; вручную: Корзина | Система; Администратор |
| Архив | Автоматически после изменения статуса ГК на «Архив» | — | Система |
| Корзина | Вручную из «Черновик», «В работе», … | Вручную: Черновик, В работе, Оплачено | Администратор |

### 4.1.4. Работа/Заявка
| Статус | Присвоение | Переходы | Кто |
|---|---|---|---|
| В работе | Вручную при создании пользователем с ролью «Подрядчик»… | Авто: Оплачено; вручную: Корзина | Система; Подрядчик, Администратор, Руководитель проекта |
| Оплачен | Автоматически при проставлении статуса «Оплачено» в Этапе ГК | — ; вручную: Корзина | Система; Администратор |
| Архив | Автоматически после изменения статуса Этапа на «Архив» | — | Система; Администратор |
| Корзина | Вручную из «В работе», «Оплачено» | Вручную: В работе, Оплачено | Администратор |

### 4.1.5. Общие правила реестров Архива/Корзины
- Для каждой сущности создаются отдельные реестры «… (Архив)» и «… (Корзина)»; путь: Главное меню → Расчет по методике 3-Р → НСИ → Архив/Корзина.
- В архивном реестре отображаются только записи со статусом «Архив»; запись перестаёт видна в основном реестре.
- Сортировка по умолчанию: «В работе» → «Завершено» → «Корзина».
- Разделы доступны ролям: Администратор, Администратор НСИ, Аналитик качества (ДИТ), Руководитель… (в списке источника обрывается — см. 07, A-3); раздел «Корзина» — только Администратору.

## 4.2. Статусные модели: СЗ, Этап СЗ, Внутренняя работа (`БП - Создание статусной модели для СЗ, Этапа СЗ и Внутренней работы`)

- **Служебное задание**: «В работе» (авто при создании) → «Завершено» (при завершении работ; доступно…) → «Архив» (автоматически через **60 календарных дней** после «Завершено»; возможен ручной перевод; восстановление из Архива — в выбранный статус) ↔ «Корзина» (ручной перевод из «В работе»/«Завершено», восстановление обратно).
- **Этап СЗ**: «В работе» (авто при создании) → «Завершено» (авто при завершении работ по этапу) → «Архив» (автоматически в момент перевода связанного СЗ в архив; ручной перевод из «Завершено»; восстановление) ↔ «Корзина».
- **Внутренняя работа**: «Черновик» (авто при создании карточки) → «В работе» (проставляется Руководителем проекта после внесения Задач) → «Завершено» → «Архив» (в момент перевода связанного Этапа СЗ в архив) ↔ «Корзина» (из «Черновик», «В работе», «Завершено»).
- Реестры отображают только соответствующие статусы; сортировка по статусу: сначала «В работе», затем остальные.
- Проверка прав: перевод статусов выполняется ролями «Руководитель проекта», «Администратор», «Администратор НСИ» (критерии приемки п.30).
- Ограничение области: реализация строго после БП статусной модели Закупки/ГК/Этапа ГК/Работы.

## 4.3. Статусы ФОИ и БП в расчётах

### 4.3.1. Конструктор РСЗ (`БП - Конструктор РСЗ`)
- Статусы БП: «В работе» (синий индикатор), «На согласовании» (жёлтый), «Согласовано» (зелёный), «На доработке».
- Кнопка «Сохранить» создаёт запись БП/ФОИ со статусом «В работе» и **блокируется при незаполнении обязательных полей**.
- Обязательные поля ФОИ: Подсистема, Функциональное требование, Наименование, Краткое описание, Трудозатраты (чел./мес.), Приоритет.
- Редактирование/удаление/дублирование БП доступно Аналитику подрядчика только в статусах «В работе» и «На доработке»; удаление заблокировано при наличии зависимостей («Система блокирует удаление БП, если существуют зависимые согласованные [РСЗ]»).
- Удаление файла БП — только для «В работе»/«На доработке».
- Выбор БП в расчёт: показываются только БП в статусе «Согласовано», привязанные к текущему ГК (функции 8.3.1–8.3.2).
- Цветовая подсветка строк таблицы: зелёный — «Согласовано», жёлтый — «На согласовании», красный — «Не согласовано».

### 4.3.2. In-line таблица ФОИ (`БП - Работа с расчетами, как с таблицами в Excel`)
- Новая ФОИ из кнопки «Добавить пустую ФОИ» создаётся в статусе «Черновик» с автозаполнением от типовой ФОИ по выбранному ФТ.
- In-line редактирование разрешено только для «Черновик» и только полей «Уточняющая часть наименования» и «Краткое описание»; для остальных статусов — только через модальное окно.
- Перевод в «В работа» невозможен, если любое из двух полей пусто (сообщение об ошибке); после перевода in-line блокируется.

### 4.3.3. Перепривязка итераций (`БП - Изменение процесса работы с ФОИ внутри итераций`)
- BR-ITER-01: при переводе ФОИ в «Согласовано» старая связь с итерацией удаляется, создаётся связь с актуальной итерацией (атрибут «ID итерации» обновляется). Если ФОИ уже в актуальной итерации — ничего не происходит.
- BR-ITER-02: при создании новой итерации все согласованные ФОИ автоматически перепривязываются к ней.
- BR-ITER-03: при статусе расчёта «Согласовано» изменение статусов ФОИ заблокировано; сообщение: «Изменение статусов ФОИ недоступно. Расчёт находится в статусе "Согласовано". Для внесения изменений создайте обращение в СТП.»
- BR-ITER-04: откат статуса расчёта администратором не создаёт новую итерацию; новая итерация появляется только при переводе расчёта из «На согласовании» в «В работе».
- BR-ITER-05: Аналитик ДИТ вправе менять статус согласованной ФОИ (в т.ч. на «Не согласовано», «В работе») при статусе расчёта ≠ «Согласовано».

### 4.3.4. Окно корректировки статусов на этапе РП (`БП — Изменение статуса ФОИ пока РСЗ на согласовании`)
- BR-FLOW-01: менять ранее выставленный статус ФОИ можно, пока РСЗ находится на шаге «Согласовано РП» и до перевода РСЗ в следующий статус («Доработка» или «Согласовано»); доступ — по матрице ролей.
- Примечание: это правило конфликтует с формулировками 4.3.3 (см. 07, C-1).

### 4.3.5. ФОИ из НМЦК и фиксированная стоимость (`БП - Статус ФОИ с фиксированной стоимостью`)
- Матрица переходов: «В работе» (авто при добавлении ФОИ из НМЦК; вручную: Согласовано, Не согласовано; авто: На согласование) → «На согласование» (переводят Аналитик Подрядчика, Администратор; Администратор может менять статус из любого) → «Согласовано» / «Не согласовано» (переводит Аналитик ДИТ; из «Не согласовано» — обратно в «В работе»/«На согласование»).
- Права на редактирование: в «В работе» и «Не согласовано» редактирование доступно Аналитику Подрядчика; в «На согласование» — недоступно; в «Согласовано» — поле «Краткое описание» становится неизменяемым.
- Индикатор «Проверка ФОИ» на ЭФ «Перечень ФОИ из НМЦК по этапу»: состояния «Присутствуют ФОИ в статусе "Не согласовано"», «Все ФОИ согласованы», «ФОИ в процессе проверки», «Дополните поле "Краткое описание"…» — с текстами подсказок при наведении.
- Сортировка реестра: первыми — «Не согласовано».
- Кнопка «Скачать замечания» активна только при наличии ФОИ в статусе «Не согласовано».
- Метка «Статус функции в ОД» в реестре «НМЦК фиксированная стоимость»: функция не скопирована → статус не отображается; скопирована и «В работе» → «В работе»; «Согласован(о)» → «Согласовано».
- Наименования статусов ФОИ по заявке на ЭФ «Итерация» приведены к единому виду (Согласовано/Не согласовано вместо Согласован/Не согласован).
- Ответственный аналитик назначается администратором — один на весь перечень ФОИ фиксированной стоимости ГК; ответственный подрядчик выбирается из пользователей, связанных с контрагентом; хранение истории статусов; email-уведомления по шаблонам источника.

## 4.4. Правила проверки НСИ перед расчётом (`БП - Проверка заполненности НСИ, значения из которых нужны для РСЗ`)

- BR-NSI-01: кнопка «Проверить коэффициенты расчета» отображается только для расчётов в статусе «На согласовании у РП», на месте кнопок «Расчет стоимости заявки»/«Протокол стоимости заявки»; доступна ролям РП ДИТ и Администратор. Цвет: серый → зелёный после успешной проверки + уведомление «Проверка выполнена успешно. Коэффициенты корректны».
- BR-NSI-02 (создание/развитие): проверка активируется, если есть хотя бы одна ФОИ с признаком «рефакторинг = false». Проверяются поля блока «Создание/Развитие» вкладки «Доп. сведения по ГК»: стоимость 1 чел-мес; итого количество ФТ; общие расчётные трудозатраты — значения не должны быть 0/пустыми. Коэффициент пересчета: > 0 и ≤ 1.
- BR-NSI-03 (рефакторинг): активируется при наличии хотя бы одной ФОИ «рефакторинг = true». Проверяются аналогичные поля блока «Рефакторинг» + по каждой подсистеме: уровень языка разработки, коэффициент переписывания ПО, количество ФТ, коэффициенты трудоёмкости **МТ1–МТ8: ровно 8 записей, без null/0**.
- BR-NSI-04: при ошибках — динамическое модальное окно (текст доступен для копирования; скролл; по возможности динамический размер) с автоподстановкой наименования системы/номера ГК/номера заявки; кнопка «Обратиться в ДИТ.Вопрос» → редирект в Telegram-чат-бот @dit_int_bot; закрытие окна сохраняет блокировку перевода статуса РСЗ.
- BR-NSI-05: проверки не изменяют данные (только контроль).

## 4.5. Правила дублирования (`БП - Запрет…`, `БП — Проверка US…`, `БП — Изменение статуса ФОИ…`)

- BR-DUP-01: запрещено создание двух работ/заявок с одинаковым наименованием в рамках одного этапа/ГК (ФЛК при создании).
- BR-DUP-02: поле «Номер заявки» — максимум 3 символа.
- BR-DUP-03: проверка US на дублирование среди Заявок и Работ в рамках ГК; при совпадении — выделение красным, обязательное поле «Обоснование дублирования задачи», ссылка в «Дублируемая задача», блокировка сохранения до заполнения.
- BR-DUP-04: исторические дубли обрабатываются только при действиях по редактированию/добавлению/удалению записей; при просмотре/обновлении/скачивании данных проверка не выполняется (DITINT-2272).
- BR-DUP-05: для ранее созданных Заявок с «Расчет» ≠ «Согласован» поле обоснования становится обязательным при наличии дубликатов; сохранение блокируется до заполнения.

## 4.6. Децимальный номер документа (`БП - Заполнение децимального номера…`)

Единая схема 8 полей для ЭФ «Формирование ЧТЗ/ПЗ/ПМИ по заявке» (вместо поля «Шифр документа без ЛУ»):
1. «Код организации разработчика» — автопредзаполнение из НСИ: реестр организаций → карточка → поле «ОГРН».
2. «Номер ОКВЭД закупки» — автопредзаполнение из карточки ГК поля «ОКВЭД закупки» (новое обязательное поле ЭФ добавления ГК).
3. «Порядковый регистрационный номер системы» — вручную; ФЛК: ровно 3 цифры, диапазон 001–999; обязательно.
4. «Код документа» — автопредзаполнение: ЧТЗ → «ПТ»; ПЗ → «П2»; ПМИ → «ПМ».
5. «Порядковый номер документа одного наименования» — вручную, необязательно.
6. «Номер редакции документа» — вручную, необязательно.
7. «Номер части документа» — вручную, необязательно.
8. «Признак документа, выполненного на машинных носителях» — вручную, необязательно; ФЛК: только символ «М».
Дополнительно: обязательное прочтение приложения «типовые коды документов.docx» перед заполнением.

## 4.7. Ставка НДС в ПОЗ (`БП - изменение ставки НДС с 20 на 22% в ПОЗ`)

- Основание: Федеральный закон № 425-ФЗ; повышение НДС с 20% до 22% с 01.01.2026.
- BR-VAT-01: дата перехода РСЗ в «Согласовано» в 2025 → 20% в ПФ ПОЗ и в РСЗ; в 2026 → 22%; несогласованные РСЗ (статусы «в работе», «на согласовании у РП», «на согласовании у аналитика») → 22%.
- BR-VAT-02 (шаблоны): для всех ПОЗ по новой методике независимо от даты согласования — 22%; по старой методике независимо от даты — 20%.
- BR-VAT-03: в файле РСЗ столбцы Z, AB, AD — статичный текст ставки; столбцы Y, AA, AC — учёт НДС в формулах.
- BR-VAT-04 (частные случаи): расхождение дат согласования в Калькуляторе и ЭДО (согласован в 2025 с 20%, но в ЭДО согласован/не согласован в 2026) — изменение ставки только через обращение в СТП.
- Версии шаблонов: Int_calc_1.0.13 (развитие/рефакторинг), Int_calc_1.0.15 (развитие+рефакторинг) в вариантах НДС 20%/22%; Шаблон_ПОЗ_старая_методика_1_0_16_v_1 с НДС 20%/22%; обновлённые шаблоны РСЗ.

## 4.8. Расчёт и вывод трудозатрат по US (`Бизнес постановка на добавление трудозатрат по US в ПОЗ`)

- Новый тег `{issue_personMonths}` во всех четырёх шаблонах ПОЗ — трудозатраты (чел.-мес.) на реализацию функций одного ФТ (US) в рамках подсистемы.
- Округление до двух знаков после запятой — для каждой подсистемы и каждой US; реализуется методом `.Round` серверного метода `ServerMethodGetPOZReportDataService` (строка 616 кода по источнику).
- Генерация: серверный метод формирует json-объект → система подставляет значения по ссылкам на поля в шаблон → файл ставится в очередь на скачивание.

## 4.9. Единый вид незаполненных данных в ОД (`БП - Незаполненные данные привести к единому виду в ПФ ОД`)

- BR-DATA-01: все отсутствующие значения в печатных формах ЧТЗ, ПЗ, ПМИ выводятся как **«undefined»** (вместо Null/«Не заполнено»/«Отсутствует описание функционального требования» и др.).
- BR-DATA-02: в таблицах без данных создаётся строка со значением «undefined».
- BR-DATA-03: унификация применяется и к документам внутри архивных выгрузок («Скачать архив (ЧТЗ + Приложения)», «Скачать архив (ПЗ + СП + БП)», «Скачать архив (ПЗ + Приложения)»).
- BR-DATA-04 (известные дефекты): несоответствия шаблона/ЭФ/ПФ в ПМИ («Качественные характеристики», «Перечень проверок», «Подготовка к испытаниям») — задача DITINT-3417; после устранения — тоже undefined.

## 4.10. Правила замен ФОИ/ФТ из НМЦК (`БП - замена ФОИ из НМЦК…`, `БП - Карточка служебного задания (СЗ)`)

- Замена возможна, только если у исходной задачи нет связанных ФОИ и/или БП; иначе блокировка с сообщением (полный текст в источнике).
- Исходное значение сохраняется (прослеживаемость); новая задача группируется с исходной; каскадное удаление исходной задачи удаляет замену (если у замены нет своих ФОИ/БП).
- Выключенный чек-бокс «Заменить ФОИ» блокирует поля «ФОИ» и «Уточняющая часть наименования ФОИ» (остаётся только «Краткое описание»).
- Реестр замен ФОИ по ГК выгружается в Excel; при отсутствии замен — файл с одними заголовками; печатные формы не меняются, если замен не было (DITINT-2261).

## 4.11. Правила интеграций (выборка бизнес-правил)

- BR-INT-01 (СПУ/Техпортал): ежедневная синхронизация активных карточек в 23:00; обработка очереди сообщений каждые 5 минут; принудительный запрос — только Администратор.
- BR-INT-02 (ДИТ.НСИ): ретраи соединения — 3 попытки с интервалом 10 минут, далее уведомление администратору; журнал циклов («Успешно»/«Ошибка связи»).
- BR-INT-03 (ДИТ.Мета): загружаются только опубликованные и актуальные записи структур БД; ручное обновление — по правам.
- BR-INT-04 (СПУР): каждый запуск цикла создаёт новый экземпляр документа в СПУР; старые экземпляры сохраняются, но исключаются из актуальной синхронизации; обязательный correlationId в каждом вызове; защита от повторной обработки сообщения и дублей экземпляров при техническом повторе; при откате согласования блокировка снимается; запрет подтверждать частично успешную синхронизацию без явно определённого правила (E3).
- BR-INT-05 (Telegram): публикация новостей — только Администратор; обработка ошибок API/сети с уведомлением пользователя.

## 4.12. Прочие зафиксированные правила

- BR-MISC-01: период работы по заявке не может выходить за срок этапа ГК (`БП - В интерфейсе РП периоды…`).
- BR-MISC-02: описание ФОИ из НМЦК — минимум 300 символов (`БП - Проверка описания ФОИ из НМЦК на 300 символов`).
- BR-MISC-03: при переводе ФОИ в «Не согласовано» обязательно указывается замечание (модальное окно справочника замечаний) (`БП - Внедрение справочника замечаний к РСЗ`).
- BR-MISC-04: выгрузка комментариев при нескольких итерациях — от последней к первой; для согласованного РСЗ действуют специальные правила включения комментариев к ФОИ/РСЗ (`БП - Выгрузка замечаний к РСЗ`).
- BR-MISC-05: «Дней до окончания» = плановая дата окончания этапа − текущая дата; отрицательное значение и просрочка при Готовности ОД < 100% → красная подсветка, ≥ 0 → зелёная (`БП - Календарный план ГК/СЗ`).
- BR-MISC-06: агрегирующие столбцы диаграмм загрузки считаются автоматически как сумма In-house + Outstaff; доли сотрудников — значения 0,25 / 0,5 / 1 (`БП на реализацию диаграмм…`).
- BR-MISC-07: удаление папки Базы знаний запрещено, пока в ней есть статьи/вложенные папки (`БП MVP1…`).
- BR-MISC-08: онбординг-презентация Базы знаний автозапускается при первом входе для всех ролей, кроме Администратора (`БП - База Знаний Калькулятора`).
- BR-MISC-09: при изменении статуса РСЗ из «Согласовано» в любой другой — при каждом последующем сохранении ЭФ «Итерация» БП заново переносятся в ЧТЗ без задвоения (`БП - Изменение логики для подтягивания БП в ПЗ и ЧТЗ`).
- BR-MISC-10: согласующие пользователи имеют множественный выбор; при выборе нескольких компаний заказчика на титульные листы попадают все согласующие сотрудники этих компаний (`Бизнес постановка изменение организации заказчика`).
